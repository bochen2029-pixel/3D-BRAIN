## What's solid (verified by reading)
- **I1 presynaptic ownership** — `k_scatter` writes `c.weight[e]` only for its own fired row `i`; each
  neuron fires ≤1×/step (atomic-once in gather) ⇒ rows are unique ⇒ no weight-write race. Ring writes
  correctly use `atomicAdd` (many→one). ✔ (`sim.cu:93–113`)
- **I2 ring safety** — gather clears `slot=step%D`; scatter writes `(step+db)%D` with `db∈[1,D-1]`, which
  is never `≡0 (mod D)`, so no write lands in the slot being cleared this step. ✔ (`sim.cu:32,37–38,102`;
  clamp `connectome.cu:122–123`)
- **I3 kernel order** — gather→scatter→(gain) serialized on the default stream (`main.cu:164–182`). ✔
- **I5 conservation of identity** — `A_t` recorded via device→device copy of `*spikes.count` immediately
  after gather, before scatter (`main.cu:167`). ✔
- **Determinism / reproducibility** — one `seed` fixes connectome, Izhikevich heterogeneity, and RNG init;
  the connectome count-pass and fill-pass run the *same* per-row RNG sweep so CSR offsets match the edges.
  ✔ (`connectome.cu:60–130`)
- **Memory footprint** — CSR ~180 MB + ring ~26 MB + state; well within 16 GB. ✔
- **Izhikevich heterogeneity** is faithful to Izhikevich (2003): exc uses `r²` for `c,d` (RS→CH), inh uses
  `r` for `a,b` (FS). ✔ (`main.cu:55–63`)

## HIGH

### H1 — `-use_fast_math` likely defeats the I4 `isfinite` guard  ·  `sim.cu:57`
`if (!isfinite(v)) v = 30.0f;` is the only blow-up guard. **Every sweep binary is built with
`-use_fast_math`** (all `tools/sweep*.ps1`), which lets nvcc assume finite operands and can fold
`isfinite(v)` to a constant `true` — silently removing the guard. This is the exact risk flagged in
`CLAUDE.md` "Known risks," and it is *active* for every result we've analyzed this session.
- **Impact:** if any neuron's quadratic term diverges, NaN/Inf can enter `A_t` uncaught and propagate.
- **Evidence it may be benign in practice:** all observed `activity.csv` are finite, sane integers, so
  either these configs don't actually diverge or the guard survived — but the safety net is **unverified**.
- **Suggest (not applied):** (a) inspect PTX/SASS for the `isfinite` branch under fast-math; or (b) replace
  the `isfinite` reset with an explicit range clamp `v = fminf(fmaxf(v,-100.f),30.f)` that fast-math cannot
  legally remove; or (c) drop `-use_fast_math` on `sim.cu` only. A one-off divergence stress-test
  (deliberately supercritical config) would confirm whether garbage is caught.

### H2 — the numeric guard is mis-ordered; recovery variable `u` is never guarded  ·  `sim.cu:52–61`
Order is: two half-steps update `v` (may be huge) → **`u += dt*(a*(b*v − u))` uses the still-huge `v`**
(`:56`) → *only then* `v` is clamped (`:57`). So a diverging `v` contaminates `u` **before** `v` is reset,
and `u` has no guard of its own. A corrupted `u` re-enters `v` next step via `−u`, and the `isfinite(v)`
clamp will keep firing the neuron (v→30 each step) while `u` stays ±Inf → a **stuck always-firing neuron**
that adds a small constant to `A_t` indefinitely. I4 ("never emit NaN/Inf into state") can be violated on `u`.
- **Impact:** latent, subtle — a few stuck neurons would inflate `A_t` slightly without an obvious NaN.
- **Suggest (not applied):** move the guard **before** the `u` update, and guard `u` too (clamp or
  `isfinite` reset). Cheap grep-test: after a run, check for neurons that fire every step.

## MEDIUM

### M1 — live `mhat_regression` is the *naive, contaminated* estimator  ·  `sim.cu:137–147`, printed `main.cu:191`
This is OLS slope of `A[t+1]` on `A[t]` — the same estimator that reads ~1 on dead/drive-dominated nets,
i.e. the exact bug that was fixed in `tools/analyze.py::mr_branching_ratio` this session. The per-step
`m_hat` in the run log is therefore **not trustworthy** (a dead run prints `m_hat≈1`). It is labeled
"cheap/subsampling-biased" in comments and verdicts use `analyze.py`, so this is a *consistency/foot-gun*
issue, not a wrong result. **Suggest:** relabel the live print `m_hat(naive)` or port the liveness+detrend
fix; otherwise a casual reader of `sim.log` will over-read it.

### M2 — wiring "probability" can exceed 1  ·  `connectome.cu:116–117`
`prob = scale·exp(−d/λ)·mod_bias`, and `scale = TARGET_OUTDEG/wsum`. In a dense same-column neighborhood
`prob` can be `>1`, so `urand < prob` is always true — those candidates connect deterministically and the
row's out-degree exceeds `TARGET_OUTDEG`. **Impact:** `TARGET_OUTDEG` is a soft target, and degree is
skewed toward dense cores. Not a crash; a modeling nuance worth documenting or capping.

### M3 — `avalanches.csv` (C++ `detect_avalanches`) is superseded and misleading  ·  `sim.cu:151–159`, `main.cu:211`
The device-side avalanche detection bins at raw `dt` with `thr=0` — the fragment/merge-confounded
convention the whole `analyze.py` IEI-binning exists to replace. `analyze.py` recomputes avalanches from
`activity.csv` and ignores `avalanches.csv`. So this output is vestigial and, if anyone reads it directly,
misleading (its τ is the confounded one). **Suggest:** stop writing it, or header-comment it as
"diagnostic only — analyze.py is authoritative."

### M4 — `brain.h` over-labels the C++ probe as "the acceptance instrument"  ·  `brain.h:90–95`
Doc drift: the real acceptance instrument is `tools/analyze.py` (+ the new `bp_validate.py`/`admiss.py`).
The header comment predates the analyze-centric workflow. Harmless but should be corrected so the contract
surface doesn't misdescribe the source of truth.
